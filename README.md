# Mini Expense Tracker

A small cross-platform Flutter app for tracking personal expenses, built with
**Flutter + GetX + Firebase** (Firebase Auth for accounts, Cloud Firestore for
data).

A logged-in user can add, view, edit and delete their own expenses, see
all-time and current-month totals, filter and search the full list, and switch
between light and dark mode. Every screen handles loading, empty, validation and
error states.

## 1. Setup

### 1.1 Create the Firebase project

1. Create a project at [console.firebase.google.com](https://console.firebase.google.com).
2. Open **Build → Authentication → Get started**, then enable the
   **Email/Password** provider. (Leave "Email link" off — this app uses a
   password.)
3. Open **Build → Firestore Database → Create database**. Pick a region and
   start in **production mode**; the rules in the next step replace the default
   ones anyway.
4. Open **Firestore Database → Rules**, replace everything with the contents of
   [`firestore.rules`](firestore.rules), and press **Publish**.

   There are no tables to create. Firestore makes a document the first time the
   app writes one. The shape the app uses:
   ```
   users/{userId}                       → profile: name, email, createdAt
   users/{userId}/expenses/{expenseId}  → amount, category, date, note,
                                          createdAt, updatedAt
   ```

   Each user's expenses live underneath their own document, so "you may only
   touch your own folder" is the whole security model.

### 1.2 Connect the app to the project

The keys live in `lib/firebase_options.dart`, which is generated for you:

```bash
dart pub global activate flutterfire_cli
flutterfire configure
```

Pick your Firebase project, then pick the platforms you want (Android, iOS, web,
…). The command overwrites `lib/firebase_options.dart` with the real keys and
drops in the per-platform files Firebase needs
(`android/app/google-services.json`, `ios/Runner/GoogleService-Info.plist`).

The version of `firebase_options.dart` committed here is a placeholder full of
`REPLACE_ME`. Until you run the command above, the app starts on a short
"Firebase is not set up yet" screen instead of crashing — see
`FirebaseService.start()`.

These keys are safe to ship in a client app; they only identify the project.
What a user may actually read or write is decided by the Firestore rules.

### 1.3 Run

```bash
flutter pub get
flutter run
```

### 1.4 Verify

```bash
flutter analyze             # 0 issues
flutter test                # 56 tests
```

## 2. How it behaves

- Sign up asks for a name, email and password. Firebase Auth creates the
  account and signs the user straight in, so a new user lands on the dashboard
  without logging in a second time. The name is saved both on the Firebase Auth
  account (`displayName`) and in the `users/{uid}` document.
- The login is remembered by the Firebase SDK, so the user stays logged in
  across app restarts. On start-up the splash screen asks
  `AuthController.resolveStartRoute()` where to go.
- If the login is still valid but the profile document cannot be read (offline,
  for example), the app keeps the session and falls back to the name and email
  Firebase Auth already knows, instead of logging the user out.
- If Firebase signs a user out on its own — deleted account, expired token —
  `AuthController` notices through `AuthRepository.isSignedIn` and returns to
  the login screen with the cached expenses cleared.
- Amounts must be greater than 0, the category is required, and dates cannot be
  in the future. The same amount/category/date rules are repeated in
  `firestore.rules`, so they hold even if a request does not come from this app.

## 3. Project structure

```
lib/
├── firebase_options.dart          # generated by `flutterfire configure`
├── main.dart                      # start Firebase → prefs → GetMaterialApp
└── app/
    ├── bindings/                  # InitialBinding: app-wide dependencies
    ├── controllers/               # AuthController, ExpenseController, ThemeController
    ├── core/
    │   ├── theme/                 # AppColors, AppTheme (light + dark)
    │   ├── utils/                 # Validators, Formatters, AppDialog, AppSnackbar
    │   └── values/                # AppStrings, AppDimens
    ├── data/
    │   ├── enums/                 # LoadingState, ExpenseCategory
    │   ├── models/                # AppUser, Expense, CategoryTotal, Result
    │   ├── repositories/          # AuthRepository, ExpenseRepository (+ Firebase versions)
    │   └── services/
    │       └── firebase_service.dart   # starts Firebase, hands out Auth + Firestore,
    │                                   # turns errors into readable messages
    ├── global_widgets/            # AppButton, AppTextField, ExpenseTile, chart, state views
    ├── modules/                   # one folder per screen: bindings / controllers / views
    └── routes/                    # Routes + AppPages
firestore.rules                    # security rules = who may read/write what
```

Data only ever flows one way:

```
View  ──►  Controller  ──►  Repository  ──►  FirebaseService  ──►  Firebase
  ▲            │
  └── Obx ─────┘   (reactive state)
```

## 4. Design decisions

**Why one shared `ExpenseController`?**
The dashboard and the list screen show the same data in two shapes. Giving each
screen its own copy would mean re-fetching after every write and risking numbers
that disagree. Instead there is a single `RxList<Expense>`; the dashboard totals,
the chart and the list are all derived from it, so any create/edit/delete is
reflected everywhere in the same frame. `ExpenseListController` only holds the
filter and search state and filters that shared list — it never stores rows.

**Why `Result<T>` instead of exceptions?**
Repositories catch Firebase errors and return `Result.ok` / `Result.fail` with a
message that is already safe to show a user.
`FirebaseService.describeError` translates `FirebaseAuthException` codes
(`invalid-credential`, `email-already-in-use`, …), Firestore codes
(`permission-denied`, `unavailable`) and connection failures into plain
sentences. Controllers then have one uniform shape to handle, and no UI code
ever sees a raw exception.

**Why keep expenses in a subcollection?**
`users/{uid}/expenses/{id}` means the owner is part of the path. The rules stay
two lines long, a query cannot accidentally be written without its owner filter,
and sorting by `date` needs no composite index — Firestore indexes single fields
automatically.

**Why store `category` as a string key?**
`ExpenseCategory` is an enum with a stable `key` ('food', 'transport', …) that is
what lands in Firestore. Labels and icons can be renamed freely, and
`ExpenseCategory.fromKey` falls back to `other` for unknown values, so a document
written by a newer build can never crash an older one.

**Why write `date` as a midnight `Timestamp`?**
Firestore has no date-only type. `Expense.toMap` drops the time before saving so
the day cannot drift by one when the value is read back, while `createdAt` /
`updatedAt` keep their full time and are only used for ordering and display.

**Security.** Every read and write is checked server-side by
`firestore.rules` against `request.auth.uid`. The app also only ever builds paths
under the signed-in user's own document, so the intent is explicit in the code
too.

**State management.** `Rx` fields + `Obx` throughout — one pattern, used
consistently. `GetView<T>` gives every view typed access to its controller, and
each route declares a `Bindings` so controllers are created on navigation and
disposed when the screen closes. `ExpenseController`, `AuthController` and
`ThemeController` are registered as `permanent` because they are app-wide state.

## 5. Tests

```bash
flutter test
```

- `test/unit/validators_test.dart` — email, password, amount and name rules
- `test/unit/expense_model_test.dart` — reading and writing Firestore documents,
  `AppUser` display name/initials
- `test/unit/expense_controller_test.dart` — loading/empty/error transitions,
  sorting, totals, month filtering, create/edit/delete success **and** failure
  paths, `clear()` on logout (uses an in-memory fake repository — no network)
- `test/unit/expense_list_controller_test.dart` — category filter, search,
  combined filters, clearing filters
- `test/widget/expense_tile_test.dart` — row rendering, tap/delete callbacks,
  per-row deleting spinner, no-note layout
- `test/widget/state_views_test.dart` — empty state, error state + retry, and
  that `AppButton` blocks taps while loading

Because the repositories sit behind abstract classes, the controller tests swap
in a fake and never touch Firebase.

## 6. Known limitations

- Firestore's offline cache is not turned on, so the app expects a connection.
  Failures are reported with a retry action rather than queued.
- The currency symbol is fixed to `$` in `Formatters` — there is no per-user
  currency setting.
- Editing the profile name is not implemented (the requirement was to display
  account information only).
- Expenses are fetched once per session and kept in memory; a Firestore
  `snapshots()` listener would push live changes from another device.
- Copy is English-only; all strings are centralised in `AppStrings`, so adding a
  localisation package later is a mechanical change.
